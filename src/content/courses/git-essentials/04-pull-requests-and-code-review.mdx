In professional engineering teams, developers rarely push directly to `main`. Instead, changes go through a **Pull Request (PR)** so automated CI checks and teammates can review the diff first.

## The GitHub Flow

1. Pull the latest `main`.
2. Create a short-lived feature branch (`git checkout -b fix/navbar-gap`).
3. Make small, tested commits and push your branch.
4. Open a Pull Request describing **what** changed, **why**, and **how you tested it**.
5. Address review feedback, pass CI checks, and merge (often via **Squash and Merge** to keep `main` history tidy).

<Callout type="tip" title="Keep Pull Requests Small">
  A 150-line PR gets reviewed carefully in 10 minutes. A 2,000-line PR gets skimmed or stalled for days. Split large features into smaller, shippable PRs.
</Callout>
